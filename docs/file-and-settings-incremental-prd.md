## 1. 模块一：文件管理体系

> 对应：需求原文「文件管理体系完整优化，基于 Obsidian 的竞品复刻，完整借鉴」

### 1.1 现状诊断（按严重度排序）

#### F-1【P0】笔记 id 由磁盘路径哈希生成，改名/移动后 id 会变

**证据**：`src/stores/note.js:1052` — `id: generateStableId(file.path)`，哈希函数定义在 `note.js:24`。

**用户可感知后果**：笔记的持久标识绑定的是「文件在哪」，不是「这篇笔记是哪篇」。

- 重命名或移动文件后，本次会话内 id 不变；但只要发生一次重加载（`App.vue:237` 的外部变更重载、切换工作空间、重启应用），该 id 全部换新。
- 任何持有旧 id 的东西失效：阅读视图 `ReadingView.vue` 的 `currentNote` 按 `route.params.id` 精确查找 → 书签/历史记录打开直接落到「笔记不存在」空态；关系图的选中态丢失。
- 这是下面 F-4/F-5 引入丢稿风险时的**放大器**：id 不稳定，连「我刚才那篇去哪了」都无法回答。

#### F-2【P0】文件名安全化覆盖面不足，四类非法输入未拦截

**证据**：`src/stores/note.js:335-337`

```js
function safeFileName (title, ext) {
  return `${String(title || '无标题').replace(/[\\/:*?"<>|]/g, '_')}.${ext}`
}
```

只替换了 `\ / : * ? " < > |` 八个字符。以下四类均未覆盖：

1. **Windows 保留设备名**：`CON` / `PRN` / `AUX` / `NUL` / `COM1-9` / `LPT1-9`（含带扩展名形式，如 `NUL.md`）
2. **结尾空格与结尾点**：Windows 资源管理器与多数 API 会静默剥除
3. **控制字符**（`\u0000-\u001F`）与超长文件名（>255 字节）截断
4. **同目录重名**（此处无检测，见 F-3）

**用户可感知后果**：标题写成 `CON` 的笔记在 Windows 上写盘失败或指向系统设备；标题以空格结尾时，内存里的 `filePath` 与磁盘真实文件名不一致 → 后续所有基于 filePath 的操作（保存、删除、移动）打空，**笔记静默变成孤儿**（UI 显示在库里，磁盘上找不到，重启后消失）。

#### F-3【P0】新建/保存路径无同名检测，会静默覆盖已有文件

**证据**：`saveNoteToFile`（`src/stores/note.js:1114-1140`）在 `filePath` 为空时直接由 `buildFilePath(folder, safeFileName(title, ext))` 构造目标路径后写入；主进程 `fs:write-file`（`electron/main.cjs:812-828`）是覆盖式 `fsp.writeFile`。

反差证据：**移动时会检测**——`fs:move-file`（`electron/main.cjs:914-951`）默认拒绝覆盖并返回 `{ error: 'target-exists' }`，`note.js:364` 也据此回滚。也就是说「移动有保护，新建反而没有」。

**用户可感知后果**：同一文件夹下新建两篇同名标题的笔记，后一次落盘直接覆盖前一篇内容，**丢稿且无任何提示**。

#### F-4【P0】外部磁盘变更默认完全不感知

**证据**：

- 监听只在 `'autoSync' && notesPath` 同时成立时才建立：`src/App.vue:452-454` 的 `watch([() => appStore.autoSync, () => noteStore.notesPath])` → `syncNotesWatch()`
- `syncNotesWatch`（`App.vue:228-243`）在条件不满足时直接 `stopNotesWatch()`
- **`autoSync` 默认值是 `false`**：`src/constants/storage.js:128` — `{ key: LS_KEYS.autoSync, ref: 'autoSync', parse: asBoolean, fallback: () => false }`
- `App.vue` 的 `onMounted` 只做了一次 `loadNotesFromPath`，不建立监听

**用户可感知后果**：默认安装后，用户在资源管理器、其它编辑器、云同步盘里对 `.md` 做的任何改动，本应用**一概不知**。此时在本应用里继续编辑并保存，会把外部版本覆盖回去——**双向静默覆盖**。

#### F-5【P0】外部变更处理方式是「整库全量重载」，会打断正在进行的编辑

**证据**：`src/App.vue:236-238`

```js
notesWatchUnsubscribe = window.electronAPI.onNotesExternalChange(() => {
  noteStore.loadNotesFromPath(path)
})
```

主进程侧去抖 600ms（`electron/main.cjs:698-718`，`WATCH_DEBOUNCE_MS`），并已过滤自身写入（`isSelfWrite`）——这部分做得对；问题在于回调策略本身是全量重载。

**用户可感知后果**：只要磁盘上有一个 `.md` 发生变化（外部工具保存、网盘同步落新版本、Git checkout），整个库就被重读一遍：正在编辑的笔记回到磁盘旧内容、光标/选中丢失、当前列表滚动位置重置、UI 明显闪烁。开了「自动同步」的用户等于**随时可能被打断**。

> 说明：F-4 与 F-5 是一枚硬币的两面——因为默认关闭（F-4），大多数用户还没撞上 F-5；一旦按 S-4 把监听打开，F-5 会立刻成为高频故障。**两者必须同批处理。**

#### F-6【P1】文件监听只认笔记扩展名，附件类变更不触发刷新

**证据**：`electron/main.cjs:704` — `if (!NOTE_FILE_EXTENSIONS.has(path.extname(String(filename)).toLowerCase())) return`；白名单定义在 `main.cjs:17`：`new Set(['.md', '.markdown', '.txt'])`。

**用户可感知后果**：图片、PDF 等附件的新增/删除完全不触发任何刷新（配合 D-8「附件本身也不支持」，图片类使用场景整体不可用）。

#### F-7【P1】多库（workspace）没有管理入口，只有「重置」能碰它

**证据**：`src/stores/workspace.js` 有完整的双层持久化（Electron: `userData/workspaces.json` + localStorage 降级）、迁移（`hydrate`，39-77）与缺失探测（`probe`，144-164）。但全项目对它的写操作只有一处：`reset()`（179-185），且**只在 `SettingsView.vue` 的「重置应用」里被调用**。`SettingsView.vue` 全文无工作空间管理 UI。

**用户可感知后果**：用户无法新增第二个库、无法在库之间切换、无法移除失效库（磁盘上的库被手工删掉后只能看到 `ws.missing` 标记，却无从处理）。能力建好了，但没有出口——**等于对用户不存在**。

#### F-8【P2】`buildFilePath` 用正斜杠硬拼跨级目录

**证据**：`src/stores/note.js:329-332` — `folder ? \`${base}/${folder}/${fileName}\` : ...`

**用户可感知后果**：风险很低（Node 的 fs 在 Windows 上接受正斜杠），但内存里的路径形态与磁盘原生形态不一致，导致**未来所有面向用户展示/日志记录的 path 在不同平台呈现不同**。列为 P2：作为引入日志系统（模块四）的前置清理动作顺手做掉。

### 1.3 变更需求（只描述行为，不规定实现方式）

1. **稳定标识**：笔记需拥有一个不随磁盘路径变化的持久标识。用户行为预期：给一篇笔记改名、移动、切库重载后，指向它的历史记录与书签仍然能打开它。
2. **文件名合法化**：任何标题写入磁盘前都应被落成「在当前 OS 与当前目录下一定合法且一定不重名」的文件名。用户无需关心规则，只需知道「建重名笔记不会覆盖旧的」。
3. **磁盘变更可感知且非破坏性**：磁盘上发生的外部改动应被感知；处理方式必须是**定向**的（只处理变化的那些文件），不得在用户正在编辑时把整库重读一遍；当某个文件的磁盘版本与内存版本都发生过修改时，必须让用户选择保留哪一份，**不得静默覆盖任意一方**。
4. **多库一等入口**：用户应能新建、切换、重命名、移除本地库，并能看到每个库的健康状态（存在 / 缺失）。
5. **路径表示统一**：对外展示与记录的磁盘路径在各平台保持一致形态。

## 2. 模块二：文档管理系统（用户吐槽的「很大一坨问题」）

> 对应：需求原文「修复现在文档管理系统的问题」
> 排查范围按任务要求：重命名/移动/删除后索引、双链、标签、当前打开笔记是否同步；磁盘外部变更；大库性能；文件名非法/重名/大小写/越权；附件资源；删除可恢复性

### 2.1 现状诊断（按严重度排序）

#### D-1【P0】日期归属用 `updatedAt`，不是创建时间——改名/移动会让笔记在日历里「跳到今天」

**证据**：`src/utils/noteIndex.js:165-172`，dateIndex 的键是 `dateKey: dateKeyOf(note.updatedAt)`。

而 `updatedAt` 会被这些**非内容修改**操作刷新：

- `moveNote`：`note.js:344` — `note.updatedAt = new Date()`
- `renameNote`：`note.js:425-427` 附近在处理首行标题时刷新
- `rewriteBacklinks`：`note.js:406` — 被牵连改写的笔记也刷新 `updatedAt`

放大到 UI：日历月统计同样按 `updatedAt` 过滤（`CalendarView.vue:347` 附近）。

**用户可感知后果**：这是「文档管理混乱」里**最能被用户直接撞到的一条**——用户把一篇旧笔记换个文件夹或改个标题，这篇笔记立刻出现在**今天**的日历格子里，同时从原来的日期格子里消失；「全部笔记」列表按修改时间排序时它也会窜到最前。用户感知就是"我的笔记乱了/顺序莫名其妙变了"。

> 约束提醒：修复时不能简单把 `updatedAt` 换成 `createdAt`——磁盘上没有可靠的创建时间。见「8. 待确认问题」Q1。

#### D-2【P0】重命名的双链改写是「发射后不管」，失败无处感知

**证据**：`rewriteBacklinks`（`src/stores/note.js:388-412`）内部对每张受影响的 note 调用 `safeWriteFile(n.filePath, n.content)` —— **没有 `await`**，函数本身也是同步返回 `changed` 计数；调用方 `renameNote`（`note.js:433-436`）只拿到一个数字，不知道任何一次写盘是否成功。

**用户可感知后果**：改名时 UI 提示成功，但如果某张受影响笔记当时磁盘只读/被占用，它的 `[[旧标题]]` **没有真正改掉**。内存里改了（所以当场看着正常），重启后链接回退成旧的 → 双链断、反链消失。这类漂移用户几乎无法自我诊断。

#### D-3【P0】`moveNote` / `renameNote` 对外同步返回 `true`，失败是异步回滚的

**证据**：

- `moveNote`（`note.js:339-381`）：内部 `runMove()` 异步体在 357-379 行执行，**未 await**；函数第 380 行无条件 `return true`
- `renameNote`（`note.js:424-478`）：同样结构的 `runRename()`，末尾 `return true`
- 失败路径（`target-exists` / 其它错误）是在 `runMove` 内部把 `note.folder` 回滚并 `reportSaveError`

**用户可感知后果**：DnD 拖拽或右键重命名后，UI 立即显示成功（侧边栏结构已变），几百毫秒后才可能弹错并回滚——**表现为「结构跳一下又跳回去」**。更糟的是调用链上层无法区分「真成功」与「稍后回滚」，没有任何等待机制。

#### D-4【P0】删除文件夹的确认文案与实际行为完全相反

**证据**：

- UI 文案：`src/components/Sidebar.vue:590-596` — 「该文件夹下的所有笔记会被移到根目录」
- 实际实现：`deleteFolder`（`src/stores/note.js:498-545`）在 flush 之后，把 `affected` 笔记**从库中移除**（第 515-519 行 `notes.value.splice` + `unindexNote`），再对整个目录执行 `removeDir`（第 527 行附近）→ 目录连同里面的笔记**一起进回收站**
- 只有在 `removeDir` **失败**时，才会走「笔记放回根目录」（第 534-540 行）

**用户可感知后果**：用户看到「笔记会被移到根目录」，理解为「我的笔记还在，只是挪个位置」，于是确认删除。真实结果是**整个文件夹及其笔记一起被删进回收站**。这是一条确认-预期严重错配，属于会造成用户流失的信任问题。

#### D-5【P1】删除笔记提示「不可恢复」，但实际是进回收站——且没有任何还原入口

**证据**：

- UI 文案：`Sidebar.vue:582-585` — 「确定删除这篇笔记吗？（不可恢复）」
- 实际实现：`deleteNote`（`note.js:857-888`）→ `fs:delete-file` → `main.cjs:858-879` 优先 `shell.trashItem`，失败时 `moveToLibraryTrash()` 放进库内 `.trash` 目录并加时间戳前缀

**用户可感知后果**：两个方向的错误同时存在——**乐观删除**被吓退（以为删了就没了），**误删了以为没救**（其实文件在回收站里，但应用不提供任何查看或还原入口，用户也不知道去哪找）。两个方向都是坏体验。

#### D-6【P1】搜索是全库线性字符串扫描，无预建索引

**证据**：`src/stores/note.js:201-208`

```js
const searchFiltered = computed(() => {
  const query = searchQuery.value.trim().toLowerCase()
  if (!query) return notes.value
  return notes.value.filter(n =>
    String(n.title || '').toLowerCase().includes(query) ||
    String(n.content || '').toLowerCase().includes(query)
  )
})
```

虽然作用在 `computed` 上（有计算缓存），真正的重算发生在笔记内容变化时而非每次击键。但关键问题在于：**每一次查询都要对全部笔记的标题与正文各做一次 `toLowerCase()` + `includes()`**，即 O(笔记总数 × 平均正文长度)。`SearchView.vue` 侧虽有 180ms 防抖，但防抖只降低频率，不改变单次开销。

**用户可感知后果**：笔记规模上千后，在输入框里连续输入会出现明显输入延迟（每次 commit 后被阻断一次主线程）。这是典型的「小库无感、大库用不了」。

> 诚实标注：我**没有做实际的大库性能测试**（未构造 5000 篇笔记实测响应耗时）。这里给的是复杂度推断 + 代码结构性判断，不是实测数据。建议实现阶段补一个数据量基准。

#### D-7【P1】文件级操作没有「撤回」

**证据**：`deleteNote`（`note.js:857-888`）、`deleteFolder`（`498-545`）、`moveNote`（`339-381`）、`renameNote`（`424-478`）全部无 undo 登记；编辑器内的 CodeMirror undo 栈只覆盖文本编辑，不覆盖文件操作。

### 2.3 变更需求（只描述行为，不规定实现方式）

1. **时间语义澄清**：笔记在「日历」与「按时间排序」里的归属时间，应与**内容或创建时间**相关，而不是被「改名/移动/他人文件被引修改」这类非内容操作刷新。具体基准见 Q1。
2. **rename / move 的原子性**：对用户的承诺是「要么整件事都成，要么什么都不变」。UI 不应该先显示成功再回滚；失败时应明确告知改了哪些、没改哪些。
3. **删除的可预期性**：删除前**准确**告诉用户会发生什么（哪些笔记会消失、去哪里了）；删除后提供一个可以找回来的地方。
4. **可撤回**：文件级的破坏性操作应有一步「放回原处」。
5. **规模不敏感**：搜索在几千篇规模下不应出现可感知的输入延迟。
6. **附件一等支持**：图片能看、能放进去、能跟着笔记一起被管理。
7. **展示一致性**：列表显示的扩展名必须是真实的扩展名；不提供虚假的可交互控件。

### 3.2 现状诊断（按严重度排序）

#### S-1【P0】默认笔记扩展名：设了能存，重启后就忘

**证据**：

- 写入侧：`src/stores/app.js:764-768` `setNoteExtension(ext)` → `configRefs.noteExtension.value = ext` + `localStorage.setItem(LS_KEYS.noteExtension, ext)`
- 读取侧：`src/constants/storage.js:129`

```js
{ key: LS_KEYS.noteExtension, ref: 'noteExtension', skipLoad: true, fallback: () => 'md' },
```

`loadConfig`（`app.js:245-270`）遍历 schema 时会跳过所有 `skipLoad: true` 的项 → 新会话里 `noteExtension` 永远回到 `'md'`。

**用户可感知后果**：标准的「看起来能用其实不生效」。用户把默认扩展名改成 `.txt`，下次新建确实变成 `xxx.txt`，重启后又跳回 `.md`。用户会反复去设置里改，最终认为「设置没用」。

> 注：`hotkeys`（`storage.js:139`）也是 `skipLoad: true`，但那是有意的、由 `mergeBindings` 单独处理，**不是同一个 bug**。

#### S-2【P0】`.electron-mode[data-theme='dark']` 只覆写了 12 个变量，而 `[data-theme='dark']` 覆写了约 60 个

**证据**：

- `[data-theme='dark']`（`src/style.css:221-310`）：约 60 个变量的深色覆写
- `.electron-mode[data-theme='dark']`（`src/style.css:1511-1526`）：**只有 12 个**——`--color-bg` / `--color-bg-secondary` / `--color-bg-tertiary` / `--color-surface` / `--color-surface-hover` / `--sidebar-bg` / `--content-bg` / `--titlebar-bg` / `--card-bg` + 4 个 border
- `.electron-mode`（`style.css:1494-1509`）同理，约 15 个
- 另有碎片化的 dark 覆写散落在 `style.css` 的 1765 / 1777 / 2183 / 2499 行附近（pre / code / 右键菜单）

**为什么这是 P0**：Electron 桌面端运行时 `<html>` 上同时挂着 `electron-mode` 与 `data-theme`。凡是没有被 `.electron-mode[data-theme='dark']` 显式覆写的变量，会**回落到 `:root` 的浅色值**——包括 `--color-surface-elevated`、`--color-primary-lightest`、`--reading-bg`、`--shadow-*`、`--glass-*` 等。

**用户可感知后果**：桌面端深色模式下，卡片浮层、阴影、某些背景仍然是浅色值 → 出现「深色界面里戳着一块浅色卡片」「文字和背景双双偏浅导致低对比度」这类视觉断层。**而且这类问题只在 Electron 打包后出现，dev 浏览器里看不出来**，所以长期被漏掉。

> 这正是任务里提到的「必须有四处同时改」的坑——只是实际存在的形式与描述略有差异（见 §0.1）。

## 4. 模块四：日志系统（从零建立）

> 对应：需求原文「增加日志系统」

### 4.1 现状诊断（按严重度排序）

#### L-1【P0】全项目零个日志抽象，只有裸 `console.*`

**证据**：

- `grep console src/`：33 处（`console.error` 24 / `console.warn` 8 / `console.info` 1），分布在 store / composable / view / utils
- `grep console electron/`：23 处，全部在主进程（如 `main.cjs` 的 623 / 686 / 757 / 775 / 803 / 826 / 838 / 876 / 948 / 988 等行附近）
- 无 `logger` / `Logger` / `createLogger` 等任何抽象（全项目搜索无结果）

**用户可感知后果**：三个后果同时存在——**不分级**（ERROR 与调试信息混在一起，一眼扫不出真正的问题）、**不可过滤**（用户即便打开控制台也找不到有效的自助诊断手段）、**格式不统一**（同一个 store 里 `[note] 删除文件失败:` 这类写法各行其是，无法按模块归类）。对开发侧意味着线上问题只能靠用户复述重现。

#### L-2【P0】日志不落盘，程序一关全没

**证据**：`grep -rn "createWriteStream\|logFile\|winston\|electron-log\|appendFile" electron/ src/` → **唯一命中是 `src/utils/dictionary.js:1005` 的英文单词 `"winston"`**（字典词表）。

**用户可感知后果**：

- **用户侧**：出问题（比如刚刚提到的「笔记莫名其妙不见了」「双链断了」）时，**没有任何东西可供回溯**，用户自己也无从判断发生了什么
- **支持侧**：无法让用户「把日志发给我」。所有 issue 只能靠描述重现，显著拉长定位时间
- **`vault` 密码本等高敏感模块**（`preload.cjs` 里唯一用 `SAFE_ID_RE` 白名单保护的通道）出问题时同样无迹可查

#### L-3【P1】日志对用户完全不可见，没有导出入口

**证据**：`SettingsView.vue` 全文无「日志」相关分区；`App.vue` 无任何 logger 初始化；`preload.cjs`（116 行）**没有桥接任何 logging IPC 通道**。

**用户可感知后果**：即使未来写了日志文件，用户也不知道它在哪、怎么取。求助路径仍然是「截图 + 口述」。

#### L-4【P1】无日志级别、无模块上下文、无结构化字段

**证据**：同上 33 + 23 处 `console.*` 调用，均为自由格式字符串拼接，无统一 `{ time, level, module, message, data }` 结构，无级别过滤。

**用户可感知后果**：间接伤害——无法按「只看错误」快速过滤，也无法针对某个模块（比如只关心文件监听）开调试输出。对一个正在排查文档丢失类问题的项目，这是实打实的效率成本。

#### L-5【P1】主进程与渲染进程日志割裂

**证据**：渲染进程 33 处打到 Chromium DevTools 控制台，主进程 23 处打到 stdout —— 两条出口，永不相交；只有开着终端 + 开着 DevTools 才能同时看到。

**用户可感知后果**：一次完整的问题现场（例如「 IPC 调用失败 → store 捕获 → 视图提示」）在两处各留一半，没有人能拼起来。

#### L-6【P1】没有任何脱敏规范

**证据**：主进程日志里会打印完整磁盘路径（如 `main.cjs:760` 附近的 watcher 错误、`note.js:884` 的 `[note] 删除文件失败:` 带 path 参数）；`vault.js`（479 行，**本轮未核查**）涉及密码本。

**用户可感知后果**：一旦日志可被用户导出/上传到 GitHub Issue，**用户的家目录名、笔记完整路径、可能被记录的内容片段会随之泄漏**。脱敏必须在引入日志的**同一批**做，不能等事后补。

> 对应：需求原文「优化日历 ui 和整个逻辑」

### 5.1 现状诊断（按严重度排序）

> **根因前置说明**：日历最严重的问题（笔记随改名/移动「跳到今天」）根因在 `noteIndex.js:171` 的日期键选择，已作为 **D-1（P0）** 记在模块二，本模块不重复计数，只在需求池里以 **R-C1 承接**。

#### C-1【P1】固定渲染 6 周 42 格，二月可能塞进整整两周的下个月

**证据**：`src/views/CalendarView.vue:317` — `const remainingDays = 42 - days.length`，尾部补格无条件补到下个月。

推演：当月首日为周一（`startDayOfWeek = 0`，见 `288-289` 行换算）时无前置补格；若该月为平年 2 月（28 天），`remainingDays = 14` → **整整两行显示 3 月**。反之 6 前置 + 31 天时只补 5 天。

**用户可感知后果**：同一个日历在不同月份高度一致地变形；在平年 2 月首日为周一时，**网格里一半以上不是本月**。用户看日历需要不断确认「这格到底是哪个月」。

#### C-2【P1】每个日期格最多只显示 2 篇笔记，再多一个提示弥补不了信息丢失

**证据**：`CalendarView.vue:101` — `noteStore.getNotesForDate(...).slice(0, 2)`；超出部分只显示 `+N`（112-118 行）。

**用户可感知后果**：单日笔记超过 2 篇（日记类用户极易超过）时，日历格子里看不到任何一篇的标题上下文，只剩「+5」。日历失去了「快速扫一眼今天是啥」的价值。

#### C-3【P1】日期格子重复计算：每格一次 `getNotesForDate`，渲染时又算一次

**证据**：

- `calendarDays`（`CalendarView.vue:280-335`）内部对 42 格**逐格**调用 `getNotesForDate`（第 296 / 307 / 319 行）
- 模板 `day-cell` 里又调用一次 `getDayNotes(day)`（第 101 行），并用 `Math.min(day.noteCount, 4)` 渲染小圆点（126-135 行）
- `getNotesByDate` 内部每次 `new Date(date).toDateString()`（见 `note.js` 的 `getNotesByDate`）
- `isToday` 依赖 `today` ref + 每分钟轮询 + `visibilitychange`

**用户可感知后果**：每次切月 = 42 × 多次 Date 构造 + 42 × 索引查找 × 2 遍。中等规模库下**切换月份有明显迟滞**。同时每分钟触发一次、`visibilitychange` 也会触发的今日刷新，会让用户在日历页长期停留时反复重算整个 computed。

#### C-4【P1】只有月视图，没有周/年/议程

**证据**：`CalendarView.vue` 全文（546 行）只有月视图 + 底部当天笔记卡片区块；无周视图、无年度热力图、无议程列表。

**用户可感知后果**：日历只剩「看某天有几篇」这一个用途。用户无法通过日历做「回顾这一周/这一年写了什么」，而那才是日记类产品日历的核心价值。

#### C-5【P2】新建日记是固定标题、无模板、不能选目标文件夹

**证据**：`createNoteForDate`（`CalendarView.vue:448-459`）——标题固定 `` `${dateStr} 的笔记` ``，无模板内容，无目标文件夹选择；查重用 `notes.find(n => n.title === title)`。

**用户可感知后果**：用户每天点出来的都是一篇空笔记，标题格式也无法自定义（比如想用 `2026-03-15` 而非 `2026年3月15日 的笔记`）。Obsidian 的 Daily Note 之所以有用，靠的是模板 + 目标文件夹 + 命名格式三件套，这里一个都没有。

## 6. 模块六：关系图系统

> 对应：需求原文「以及优化关系图系统」

### 6.1 现状诊断（按严重度排序）

#### G-1【P0】真正的双链（`[[ ]]`）完全没有进入关系图

**证据**：`grep -n "linkGraph\|noteIndex\|allLinks" src/views/GraphView.vue` → **0 命中**。

`GraphView.vue` 的连边来自 `buildLinks`（605-671），输入是 `generateGraph`（551-591）产出的 `extractTags` / `extractTitleKeywords` / `extractContentKeywords`（460-538），权重为 tag 2 / title 1.5 / content 0.5 —— **全部是「文本相似度」，不是用户显式建立的链接关系**。

**用户可感知后果**：这条界定了整个关系图模块的问题性质——**用户以为自己在看「我亲手建立的链接」，实际在看「标题和用词有多像」**。

- 用户明确用 `[[...]]` 关联的两篇笔记，如果标题/标签不像，图上**不连线**
- 完全没关系、但恰好都带同一个宽泛 tag 或用词接近的两篇，图上**会连粗线**
- 作为一款以「双链笔记」为目标的软件，**核心概念在核心视图里不存在**

#### G-2【P1】关系图本地重新实现了一套 tag 提取正则，与全项目标准不一致

**证据**：

- 标准实现：`src/composables/useLinks.js:258` — `const TAG_REGEX = /(^|\s)#([A-Za-z0-9_\u4e00-\u9fa5-]+)/g`（要求 `#` 前为行首或空白，字符集限定）
- 关系图实现：`src/views/GraphView.vue:462` — `const tagRegex = /#(\S+?)(?=\s|#|$)/g`（**无前置边界**，`\S+?` 匹配任意非空白）

`noteIndex.js:17` 与 `27-34` 行的注释还专门强调了 `buildSnapshot` 必须与 `useLinks.buildLinkGraph` **双向同步**——说明团队已经意识到这个风险，但 `GraphView.vue` 这条第三套实现不在同步范围内。

**用户可感知后果**：同一个正文字段，在三处提取得到不同的 tag 集合。例如 URL 片段 `http://x.com/#anchor`、代码注释 `#define` 会被 GraphView 当成 tag 捞进来，而正文其余各处（列表、标签视图、索引）按标准口径都不会 → 图上出现与实际标签系统无关的脏连线。

#### G-3【P1】布局含随机初值且不可复现，节点坐标不持久化

**证据**：`GraphView.vue:561` 附近 `generateGraph` 参与布局的初值计算带 `Math.random()`；`randomize`（881-884）= `generateGraph + startSimulation`；`resetView`（894-907）只做居中不重排。全无坐标持久化逻辑。

**用户可感知后果**：每次打开/刷新，同一批笔记的排布完全不同 → 用户没法形成空间记忆（"我上次看到那个蓝色节点在右下角"）。对 graph 视图来说**空间记忆就是核心使用价值**，布局不稳定等于这个视图的价值归零。

#### G-4【P1】重建触发的指纹不完整且脆弱

**证据**：`GraphView.vue:978-987` — watch 的指纹是 `id:title:content.length` 三段拼接，600ms 防抖后重建。

漏掉的维度：

1. **`folder`**：移动笔记到别的文件夹，指纹不变 → 图谱不更新。当前图谱的连边本来不含 folder 语义，影响有限；但一旦引入 G-1 的双链，id/路径稳定性（R-F1）与这条会互相放大
2. **内容修改但长度不变**：改几个字但字数恰好不变（比如订正错别字）→ 指纹完全不变 → **图谱不重建**，连由内容派生出来的 tag 也不更新

**用户可感知后果**：图谱里显示的是「某一时刻的快照」，且这个时刻与用户的编辑动作不同步。用户以为图谱是实时反映笔记关系的，实际上可能停留在几分钟前。

#### G-5【P1】「链接数」的语义是被错标的

**证据**：`getLinkCount`（`GraphView.vue:873-879`）统计的是 `buildLinks` 产出的**相似度边数量**，但在 UI 上这个值会被理解为「这篇笔记有多少条链接」。

**用户可感知后果**：一篇完全没写 `[[双链]]` 的笔记显示「链接数 12」，一篇手写了 12 条双链的笔记可能显示「链接数 0」。这是**直接的数据误导**，比功能缺失更糟。

#### G-6【P2】图谱搜索只匹配标题

**证据**：`GraphView.vue:299` `searchQuery`；`visibleNodes`（413 行附近）过滤条件为 `n.label.toLowerCase().includes(...)`。

**用户可感知后果**：在图谱里搜一个 tag 或某个正文关键词，搜不出任何节点。用户只能按精确标题子串找，实用性低。

### 6.2 Obsidian 参照

### 6.3 变更需求（只描述行为，不规定实现方式）

1. **双链进图**：关系图必须优先反映用户显式建立的链接关系；文本相似度只能作为可开关的补充维度，且默认权重要低于双链。
2. **标签口径统一**：图谱里的「标签」必须与全项目其它地方（列表、标签视图、索引）口径一致——同一个正文片段在任何地方解析出的标签集合必须相同。
3. **布局可复现**：打开关系图时，同一批笔记的空间排布应当保持一致，让用户能记住「哪个位置是哪一类笔记」。
4. **图谱与内容同步**：笔记内容、标题、所属位置发生变化时，图谱应当随之更新，而不是停留在某个未知时刻。
5. **指标名副其实**：图上标出的每一个数字都必须真的是它所标榜的那个含义。
6. **搜索覆盖更广**：图谱内搜索至少应能按标签命中节点。

## 7. 分批交付计划

排序原则：**先止血（P0）→ 再补基础设施（日志）→ 最后做体验（P1/P2）**。批之间有硬依赖的地方已标出。

### 第 1 批：数据安全止血（P0，必须最先做）

包含：R-F2（文件名合法化）、R-F3（同名消解）、R-D2（双链改写落盘可信）、R-D3（移动/重命名结果可信）、R-D4（删除文件夹文案与行为一致）、R-S1（扩展名持久化）、R-S3（去掉 `window.prompt`）

理由：这批全部是「会造成丢稿/信任崩塌」或直接「功能就是坏的」，且彼此独立、改动面小、便于验证。**先做可以在下一批开始前就把用户流失的主要来源堵上。**

### 第 2 批：日志系统（P0 部分）

包含：R-L1（统一抽象）、R-L2（落盘+轮转）、R-L3（主/渲染汇聚）

理由：**必须在第 3 批之前完成**。第 3 批要动路径/id/索引，是整个阶段风险最高的改动；没有日志的话，用户反馈的任何问题都无法定位。**先把听诊器准备好，再动手术。**

### 第 3 批：标识与时间语义（P0，风险最高）

包含：R-F1（稳定 id + 一次性迁移）、R-D1 + R-C1（日期归属基准修正）

理由：这两项都会改变**已持久化数据的解释方式**，属于不可逆的数据模型变更。硬依赖第 2 批（出问题要能查）。做完必须做一次完整的数据迁移验证（导出迁移前后的笔记数/日期分布做交叉比对）。

### 第 4 批：磁盘变更感知（P0/P1）

包含：R-F4（默认监听）、R-F5（定向 reconcile）、R-F6（冲突提示）、R-S4（开关自解释）

理由：**硬依赖第 1 批**（文件名稳定后，才能让 reconcile 正确匹配「磁盘上的文件 ↔ 内存里的笔记」）。R-F4 打开了监听，就必须同时交付 R-F5/R-F6，否则等于把 F-5 的风险释放给用户——**这四个不可拆开单独上线**。

### 第 5 批：可恢复性 + 性能 + 附件（P1）

包含：R-D5（最近删除/还原）、R-D7（操作撤回）、R-D6（搜索走索引）、R-C4（日历性能）、R-F7（监听覆盖非笔记文件）、R-F8（多库入口）

理由：这一批都是「对标 Obsidian 明显缺失」的能力补足，彼此无强依赖，可按子任务并行。

### 第 6 批：视图质量（P0 剩余 + P1）

包含：R-G1（双链进图）、R-S2（Electron 深色变量同步）、R-C2（日历网格）、R-C3（密度可视化）、R-C5（周/年视图）、R-G2 ~ R-G5

理由：R-G1 与 R-G3 依赖第 3 批的稳定 id（布局持久化需要稳定主键），因此排在后面。R-S2 是纯样式修复，可与任意批次并行，但建议单独发版以便对照「dev 与打包产物」的视觉差异。

包含：R-D8（图片/附件）、R-D9（真实扩展名）、R-D10（移除假复选框）、R-S5（字号单一来源）、R-S6（说明文案）、R-F9（路径统一）、R-C6（日记可配置）、R-G6（图谱搜索 tag）、R-L7（复制诊断信息）
